# ADR 0015: Appointment persistence — slot columns and exclusion constraints

- Status: Accepted
- Date: 2026-11-10

## Context

ADR 0014 left the "no double booking" rule to two parties: the booking use
case, which loads the overlapping appointments and refuses with a 409, and
the database, which must catch the race where two simultaneous bookings both
passed that check. A unique index cannot express "no two *overlapping* time
ranges", and EF Core has no model support for PostgreSQL exclusion
constraints, while ADR 0004 says migrations are generated, not written.

## Decision

- **The slot is an EF Core complex property** in two `timestamptz` columns,
  `slot_start` and `slot_end`. It has value semantics like the domain record
  (replacing the slot on `Reschedule` updates both columns) and needs no key
  or table of its own. The domain gets a private rehydration constructor
  without the slot, because EF Core cannot pass a complex property to a
  constructor; it sets the slot from its columns right after.
- **Two exclusion constraints back ADR 0014's two clash rules**, over the
  half-open range `tstzrange(slot_start, slot_end, '[)')` and only for the
  statuses that hold the bay (`Scheduled`, `CheckedIn`):
  - `ex_appointments_bay_id_slot`: `bay_id WITH =, range WITH &&`
    (two vehicles on one lift),
  - `ex_appointments_vehicle_id_slot`: `vehicle_id WITH =, range WITH &&`
    (one car in two bays).

  `'[)'` matches `AppointmentSlot.Overlaps`, so back-to-back bookings pass,
  and the `WHERE` clause matches `Appointment.OccupiesBay`, so a cancelled
  slot or a no-show can be rebooked at once. Equality on a `uuid` inside a
  GiST index needs the `btree_gist` extension, which *is* in the model
  (`HasPostgresExtension`) and therefore created by the generated migration.
- **Raw SQL in a generated migration, as a narrow exception to ADR 0004.**
  The migration is generated by `dotnet ef migrations add` as usual; the two
  `ALTER TABLE … ADD CONSTRAINT … EXCLUDE` statements are then appended with
  `migrationBuilder.Sql` at the end of `Up`, under a comment saying why.
  Nothing generated is changed, `Down` needs nothing extra (dropping the
  table drops its constraints), and the model snapshot stays untouched, so
  `HasPendingModelChanges` keeps guarding everything EF Core can model.
  Integration tests prove both constraints exist and behave, since the model
  cannot.
- **An exclusion violation is reported like a unique violation.** It is the
  same kind of outcome — another request just stored a conflicting row — so
  `IUnitOfWork` translates SQLSTATE `23P01` into the existing
  `UniqueConstraintViolationException` with the constraint name, and the API
  answers 409 `conflict.duplicate` (ADR 0005). The booking use case still
  checks first and returns a specific error for the ordinary case.
- **Other columns follow ADR 0011:** status by name with an `IN (…)` check,
  restrictive foreign keys to bays, vehicles, customers and work orders, and
  check constraints for what is cheap to state (`slot_end > slot_start`; a
  checked-in appointment has a work order). `work_order_id` has a unique
  index: one work order is opened for at most one appointment.
- **`IAppointmentRepository.ListClashCandidatesAsync`** returns the
  overlapping, bay-holding appointments in the requested bay or for the
  requested vehicle, untracked; the use case decides with
  `ClashesInBayWith` / `ClashesForVehicleWith`, so the rule itself lives in
  the domain once and in the database once.

## Consequences

- A future change to the occupying statuses or to the overlap rule must
  update the constraints in a new migration by hand; the integration tests
  for cancelled and no-show appointments fail if they drift.
- Deleting a customer with appointments would violate
  `fk_appointments_customers_customer_id` (a 500); the booking use-case step
  extends `DeleteCustomerHandler`'s checks, as for work orders.
- The exclusion constraints' GiST indexes lead with `bay_id` and
  `vehicle_id`; the plain B-tree foreign-key indexes stay for EF Core's
  conventions and simple lookups.
